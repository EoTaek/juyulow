# NaviHelper ETA PoC 결과

실험일: 2026-11-06. 대상: [이슈 #1](https://github.com/EoTaek/juyulow/issues/1).

**보존 기록:** 실험 종료 후 PoC 실행 코드·권한·전용 테스트를 제거했다. 현재 앱은 빈 메인 화면이며, 아래 사용 절차·검증 결과는 실험 당시 구현에 대한 기록이다.

코드 구조와 ETA 조회 흐름은 [구현 참고 문서](POC_TRIP_IMPLEMENTATION.md)를 참고한다.

## 판정: 조건부 가능

`requestTrip(TripRequest)` → `onTripInfo(TripInfo)`로 임의 후보의 ETA(초)와 거리(미터)를 받을 수 있었다. POI ID와 **실측한 경로 목적지 좌표**를 대조하여 순차 조회할 수 있다. 다만 POI 중심 좌표와 응답 좌표는 다르며, 동일 후보를 재조회할 때 이전 실행의 지연 응답을 완전히 구별할 요청 ID는 없다. 이번 고정 후보 실험을 임의 주유소 전체에 대한 신뢰성 보장으로 확대할 수 없다.

이번 값은 현재 내비 위치에서 후보까지의 경로 추정치이며, 최종 목적지에 후보를 경유하는 추가 거리·시간을 증명하지 않는다. 오피넷·절약액·경유지 등록은 구현하지 않았다.

## 재현 환경과 입력

- Pleos Connect v2.1.0, Android 14, `emulator-5554`, 활성 사용자 10.
- 이미지: `RELEASE.release_connect_v2.1.0 test-keys`.
- Navigation: `ai.umos.maps.android.navigation.app` / `3.3.2-rc5-hotfix.3`.
- Navi service `3.0.4`, NaviHelper `3.0.5`, navi-data `3.0.4`.
- 화면에서 P·0 km/h를 확인했다. 내비 위치 콜백은 `(37.4127212, 127.094681)`로 고정되어 있었다. 위치 재생·이동을 실행하지 않았다. Android GPS의 last-location과 내비 위치가 같다고 가정하지 않았다.
- 호스트 네트워크를 사용하는 온라인 에뮬레이터에서 조회했다. 오프라인·패킷 손실 실험은 수행하지 않았다.
- `NAVI_ROUTE`는 대상 시스템에서 `normal` 권한이다. `NAVI_ROUTE_SEARCH`, 위치 런타임 권한, Vehicle·FusedLocation 호출은 추가하지 않았다.

내비 최근 목적지 콜백과 내비 화면에서 선택한 POI의 SearchManager 공식 검색 응답으로 식별 정보를 확보했다. 입력은 이후 고정했으며 `poiSubId`는 모두 null이다.

| --- | --- | --- | --- |
| 에시앙경북궁 | `36khq9cj8q4kcm5nqhf2` | 37.57492777, 126.97356944 | 37.5747575, 126.9734531 |

최초에는 요청 좌표에 축별 `0.000001°`만 허용했다. 첫 후보의 2302초·23725m 응답에서 ID는 같지만 좌표가 약 21.5m 달라 중단했다. 더현대서울도 약 95m 차이를 확인했다. 다른 두 후보 역시 좌표 차이로 중단했다. 실패를 성공으로 처리하거나 광범위한 반경을 허용하지 않고, 각 후보의 관측 목적지 좌표를 별도 저장했다. 최종 검증은 ID 일치 + 해당 관측 좌표에 축별 `0.000001°` 기준이다. 지도·경로·출발 조건 변경 시 재교정이 필요할 수 있다.

## 실제 SDK 실험

반복 배치 **36/36회 성공**, 최초 단일 조회 1회도 성공했다. 이 최종 반복 세션에서 `TripInfo` 109건을 수집했고, 37회 모두 전후 상태가 일치했다. 시작 버튼의 빠른 중복 입력은 차단되므로 클릭 시도 수 대신 `batch_start`와 전후 비교 완료 로그를 기준으로 센다.

| --- | --- | --- | --- |
| 안내 없음 | 2 | 3/3 | 3/3 |
| 안내 없음 | 3 | 3/3 | 3/3 |
| 안내 없음 | 4 | 3/3 | 3/3 |

| 후보 | 수신 건수 | ETA 범위(초) | 거리(m) | 응답 지연(ms) |
| --- | --- | --- | --- | --- |
| 에시앙경북궁 | 37 | 2335–2384 | 23725 | 178–280 |

| SEOULCOMMUNE | 24 | 995–1005 | 10220 | 74–116 |

배치 시간(전 상태 조회부터 마지막 TripInfo까지)은 2개 519–1532ms, 3개 610–1622ms, 4개 730–1736ms였다. 후 상태 조회 대기 시간은 이 수치와 별도이며 완료 비교 로그의 단조 시각으로 확인할 수 있다. 시간 범위는 실측값이며 SLA가 아니다.

실험 결과와 좌표 보정 근거는 이 문서에 요약했다. 저장소에는 원본 로그·압축 파일을 첨부하지 않는다. 재현 시 로그를 확인하는 방법은 아래 「사용·로그 추출」을 참고한다.

별도 세션에서 안내 중 단일 후보도 추가 검증했다. 1260ms에 수신을 완료했고 전후 상태가 일치했다. 위 표의 109건에는 이 추가 응답을 포함하지 않았다.

전후 비교는 위치, 목적지 ID·좌표, 순서 있는 경유지 ID·좌표, 안내 모드·`isRouting`·경로 옵션을 대상으로 한다. 교통 정보·남은 시간처럼 자연스럽게 변하는 필드는 비교 키에서 제외하고 원본에는 보존한다. 4종 조회가 모두 도착하기 전에는 다음 단계로 진행하지 않으며 10초 누락 시 잠근다. 콜백 자체에는 조회 ID가 없으므로 스냅샷 역시 관측 증거이며 트랜잭션 보장은 아니다.

안내 없음은 `SAFE_GUIDING`, 안내 있음은 화면의 소설한남 턴 안내·남은 시간·거리·안내 종료 버튼과 `ROUTE_GUIDING`으로 확인했다. 실제 안내 화면에서도 SDK `isRouting=false`가 관측되어 이 값을 단독 안내 활성 판정에 사용하지 않는다. 실험 준비를 위해 내비에서 목적지를 설정·안내를 시작하고 종료한 조작은 PoC 요청의 부작용과 구분했다.

소설한남의 초기 TripInfo는 1221초·17593m였으며, 이후 실제 내비 화면은 같은 지점까지 약 22분·17km를 표시했다. 시간대·교통 갱신과 UI 반올림이 있으므로 정밀 수치 일치로 해석하지 않는다. `eta`가 약 20분 수준의 소요시간으로 해석 가능한 관측값은 얻었지만, 위치를 옮겨 출발점 인과관계를 검증하지는 않았다. 응답 `routePoints`에는 목적지만 있어 정확한 출발점 식별도 불가능했다.

## 추가 실험: 후보 수에 따른 ETA 수집 시간

2026-11-06 21:31–21:34 KST에 같은 에뮬레이터와 고정 후보로 `2곳 → 3곳 → 4곳` 순서를 3회 반복했다. 정순, 주차·0 km/h, 위치 `(37.4127212, 127.094681)`, 안내 없음(`SAFE_GUIDING`) 조건이다. 앱·SDK가 이미 연결된 상태에서 단일 후보 검증 1회를 먼저 수행했으며 이 준비 실행은 통계에서 제외했다. 연결 초기화·콜드 스타트 비용을 측정한 결과가 아니며 서버/내비 캐시를 비우지 않았다.

**ETA 수집 시간**은 첫 `request` 기록 직후 `requestTrip`을 호출하기 전부터 마지막 `onTripInfo` 진입 시 `trip_raw` 기록까지의 단조 시각 차이다. 후보 사이의 콜백 처리·식별·다음 요청 실행은 포함하고, 전후 상태 조회·화면 조작·실험 배치 사이 대기는 제외한다. 후보의 주행 ETA 값을 합산한 수치가 아니다.

| 후보 수 | 1회차 | 2회차 | 3회차 | 평균 | 최소–최대 |
| --- | --- | --- | --- | --- | --- |
| 2곳 | 542ms | 488ms | 492ms | **507.3ms** | 488–542ms |
| 3곳 | 587ms | 587ms | 591ms | **588.3ms** | 587–591ms |
| 4곳 | 701ms | 752ms | 721ms | **724.7ms** | 701–752ms |

배치 시작 기록부터 전후 상태 비교 완료까지의 전체 시간은 평균 2곳 **716.0ms**, 3곳 **752.7ms**, 4곳 **898.0ms**였다. 이번 3회 평균에서는 전후 상태 확인이 순수 수집 시간에 약 164–209ms를 추가했다. 앱 연결 시간과 배치 사이 UI 조작 시간은 여기에 포함하지 않았다.

총 9개 배치의 요청 27건·원본 TripInfo 27건·목적지 일치 결과 27건을 확인했다. 9개 배치 모두 전후 상태가 일치했다. 이번 조건에서는 4곳의 ETA도 평균 약 0.725초에 수집했으나, 표본은 구성별 3회이므로 다른 네트워크·실차의 지연이나 SLA로 일반화하지 않는다.

같은 세션의 run 1은 단일 후보 준비 검증이고 run 2–10이 표의 측정 배치다. 측정값과 집계는 위 표에 남겼으며 원본 로그·집계 JSON은 저장소에 첨부하지 않는다. 시간 측정 실험에서 앱 구현은 변경하지 않았다.

## Fake·빌드·수명 검증

- 로컬 테스트: 단일 후보 게이트, 한 번에 하나의 요청, 중복 시작 차단, 완료 후보 중복 무시, 목적지 누락·불일치·다중 목적지 거부.
- 30초 타임아웃·지연 도착, 취소, SDK 오류, 동기 예외 이후 잠금과 후속 요청 차단.
- 상태 조회 누락, 실측 좌표 대조, ViewModelStore 종료 시 SDK 해제.
- 같은 후보의 과거 응답은 새 응답과 구조적으로 동일하다는 한계도 테스트로 명시했다. Fake 실험은 SDK 서버의 실제 지연·중복 전달을 재현한 증거가 아니다.
- `docs/TESTING.md`의 전체 assembleDebug·단위 테스트·lint 명령 통과. `feature:main`은 10개 테스트, 실패 0개.
- 기기 테스트 `TripProbeRecreationTest`: 실제 ActivityScenario 재생성 후 같은 ViewModelStore 유지, `OK (1 test)`. 네트워크 요청 중 재생성까지 시험한 것은 아니다.

## 실험 당시 사용·로그 추출

앱 실행 → 연결 확인 → 기본 1개 시작 → 성공 후 2~4개와 정순/역순 선택 → 시작. 요청마다 원본 초·미터와 지연을 표시한다. 중단·타임아웃·식별 실패 후에는 해당 ViewModel 세션을 다시 시작하지 않는다. 재연결·프로세스 재시작으로 이전 서버 요청이 취소된다고 가정하지 않는다.

```powershell
adb -s emulator-5554 logcat -d -v time -s TripProbe
adb -s emulator-5554 shell run-as eotaek.juyulow --user 10 ls files/trip-probe
adb -s emulator-5554 shell run-as eotaek.juyulow --user 10 cat files/trip-probe/<session>.jsonl
```

JSONL은 UTF-8이며 wall-clock 시각, 단조 시각, 이벤트 종류와 전체 SDK 데이터 클래스 표현을 보존한다. 긴 logcat 행은 잘릴 수 있으므로 분석에는 내부 파일을 사용한다. 실행 ID는 앱 내부 추적값이며 SDK 요청 식별자가 아니다.

## 채택 조건과 남은 범위

- 이번 에뮬레이터·고정 후보·위치·경로 조건에서는 후보 비교 API의 기본 가능성을 확인했다.
- 실제 주유소 데이터의 POI ID 호환성, 입구·도로 스냅 좌표 규칙, 위치 변경 시 재계산, 양산 내비·실차 호환성은 추가 확인이 필요하다.
- 임의 후보에 대해 이번 실측 좌표를 일반화할 수 없다. 응답 ID가 비거나 바뀌는 경우와 미확인 좌표는 성공 처리하지 않는다.
- SDK의 요청 ID·취소·최대 지연·중복 전달 계약이 확인되기 전에는 동일 후보 재조회 결과의 실행별 귀속을 완전히 보장할 수 없다. 미해결 요청 후 자동 재시도는 채택하지 않는다.
- 실제 지연·중복·오류 전달, 프로세스 사망 이후 미해결 요청의 동작, 실차 주행 규제·백그라운드 정책은 검증하지 않았다. 개발용 주차 PoC이며 DO를 선언하지 않는다.
